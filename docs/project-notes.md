# 项目演进记录

本项目由作者已有的 AI 伴侣原型整理而来。工程化整理日期为 2026 年 10 月 29 日；这不是原型创建日期，也不代表原型已在该日之前具备本次新增功能。

## 原始代码中已存在的功能

原型入口 `ai_partner_01.py` 使用 Streamlit 和兼容接口客户端，包含昵称与性格设置、多轮上下文、流式响应、JSON 会话保存、加载、删除和历史列表。接口指向本地 Ollama 兼容地址，模型配置为 `deepseek-r1:8b`。这表明代码进行了模型调用集成，不证明本机当前有可用模型或原型曾取得特定效果。

原目录另有 Python 基础练习、决策树演示、音视频素材、用户信息、私人会话及密钥文件。仓库只围绕 AI 伴侣相关功能重整，不收录这些无关或私有内容，也不转存来源和授权范围未核实的音视频。

## 本次工程化整理新增的功能

1. 将角色配置、会话存储、模型交互和批处理拆为独立模块，补充运行入口、依赖、配置示例和说明。
2. 用环境变量配置服务地址、模型、超时和密钥，移除原脚本中的绝对素材路径依赖；默认提供固定回复的离线模式。
3. 使用 UUID 会话编号和原子文件替换，避免同秒创建碰撞与写入过程中留下半个 JSON；拒绝不合法的文件路径参数。
4. 模型调用失败或空回复时回退本轮消息，不把未完成轮次作为成功对话保存；忽略无 choices 的流式数据块。
5. 增加兼容旧字段的结构标准化、完整轮次校验、规则脱敏、会话去重、JSONL 导出、确定性会话级划分和来源追踪。
6. 明确记录 demo / live 来源；离线模板会话不进入训练样例。旧数据来源标为 unknown，不假定已经授权训练使用。
7. 使用人工构造的正常与异常样例，编写自动化检查，并添加 GitHub Actions 工作流。

整理过程中使用了 AI 编程辅助。展示或面试时，应根据本人能够解释和修改的部分描述贡献；不能将本次辅助新增功能说成过去已经独立完成的工作。

## 关键设计取舍

**为什么采用 JSON 而不是数据库？** 当前是单机学习原型，文件便于检查旧数据和构造错误样例。代价是缺少事务、并发控制、索引与访问隔离，不能据此宣称具备高并发服务能力。

**为什么按会话划分？** 同一会话的不同 assistant 轮次共享上下文，如果逐条随机划分，容易把同一会话的重叠内容放进训练与评测两边。这里按标准化会话内容的哈希分组，所有轮次进入同一集合。它不解决跨会话近重复问题。

**为什么先脱敏再去重？** 用户编号、空白或特定联系方式的差异不应使重复内容被当成完全不同的样本。这也可能将不同用户的相似内容合并，实际项目应结合数据用途调整策略。

**为什么没有模型效果分数？** 当前评估的是程序行为和数据规则，不是模型语义质量。需要额外准备有明确标注口径的任务集、记录模型和参数，并进行人工或经过验证的模型评审后，才能报告回答质量。
